# 本地存储、迁移和恢复设计（E07）

- 日期：2026-11-03；状态：**设计与 E10 独立访问层已完成，E11 独立迁移原型进行中，应用尚未接入**。
- 关联：[技术设计](technical-design.md) · [精简开发计划](development-plan.md) · [MVP 需求](mvp-prd.md)。
- 2026-11-04 范围调整：本文是后续 SQLite 方案及原型记录；首版本地闭环保留现有 JSON 和 Pi JSONL，暂不以 SQLite 迁移、完整备份恢复作为前提。旧编号对应精简前计划归档。
- 本文规定目标行为和实施验收条件；当前应用仍使用 JSON 文件与 Pi JSONL。SQLite 访问层及隔离迁移原型已实现但未接入应用；自动迁移、备份和恢复尚未向用户启用。

## 1. 现状与问题

| 对象 | 当前实现 | 迁移范围 |
| --- | --- | --- |
| 项目、偏好、会话索引、技能、MCP、定时及运行记录 | `userData/settings.json`；单进程内 Promise 队列串行更新，写临时文件后重命名 | 迁移到应用 SQLite，保留原 ID、字段和关联 |
| 自定义网关和加密 API Key | `userData/gateway.json`；API Key 由 Electron `safeStorage` 加密 | 首版继续保留原文件及读取方式，不解密、不复制到数据库；多网关和密钥方案另行设计 |
| Pi 上下文 | `userData/sessions/<chatId>.jsonl`，由 Pi `SessionManager` 管理 | 不转换、不重写；会话 ID 与索引映射保持不变 |
| 删除对话的历史文件 | `userData/sessions-trash/` | 不迁移、不清理 |
| 项目及技能源文件 | 用户目录 | 不复制、修改或删除 |

当前 JSON 没有 schema 版本、迁移记录或面向用户的损坏恢复；状态写入队列仅覆盖同一进程，元数据与 Pi JSONL、网关文件分别持久化，不能组成跨文件事务。`settings.json` 缺失时以默认状态启动，解析错误等异常导致启动失败；暂不具备自动修复功能。

## 2. 方案决定

**正式应用元数据采用 SQLite + `better-sqlite3`，由 Electron 主进程独占业务写入；Pi 会话仍使用官方 SessionManager JSONL，网关凭据首版继续使用 `gateway.json` + `safeStorage`。** 参考 Skillkit 的主进程数据库、WAL 和原生模块打包方式，但不照搬其迁移失败后回退空库的行为。

- 选择 SQLite 的原因是项目、任务、定时和后续同步需要可事务化的索引、条件更新和版本迁移；当前整文件 JSON 适合原型，不作为长期权威存储。
- 首版只创建一个应用数据库 `userData/piwork.db`；Renderer 和 Pi worker 不直接打开它。仅在单机本地文件系统使用 WAL；其他目录和网络文件系统不作为受支持部署前提。
- 启动时申请 Electron 单实例锁，无法取得时不打开数据库、不启动调度，交由已运行实例处理；所有数据库写入集中主进程并用事务处理。SQLite 原生调用是同步的，查询需有界，不在事务中进行网络或文件系统长操作。
- 已选定 `better-sqlite3` 13.0.3；开发和打包 Electron 45.2.1 实测实际加载 SQLite 3.53.4，并通过临时库 WAL 测试。版本门禁及 `openValidatedDatabase` 辅助函数已实现和单独验证，应用当前不调用它；E10 接入数据库时必须使用该门禁。不能把 Electron 内置 `node:sqlite` 的版本误当作该模块版本；生产数据仍未迁移。
- SQLite 官方记录 WAL-reset 并发损坏问题：3.7.0 至 3.51.2 可能受影响，3.51.3 及之后修复，3.44.6 和 3.50.7 有回移修复。**启用 WAL 的发布前提**为运行时核验实际 SQLite 至少 3.51.3，或为官方明确列出的已修复回移版本，并完成目标环境测试；未满足时停止启用该方案，不静默使用旧版本或空库。单实例并不替代版本核验。[SQLite WAL 官方说明](https://www.sqlite.org/wal.html#the_wal_reset_bug)
- 加密、认证、跨端同步和 Gondolin 不因更换存储自动获得；相关方案仍按既有决定独立处理。SQLite 元数据包含路径、提示词和任务名称，应采用用户数据目录权限，不把数据库视为加密存储。

## 3. 数据模型与兼容性

E10 已实现基础模型，E11 原型将 schema 升至版本 2 并增加迁移来源记录：各实体以 JSON payload 保存完整 DTO，并对路径、MCP 归一名称及计划时间等建立列和索引；`user_version` 与 `schema_migrations` 共同记录版本。后续变更须通过版本迁移审查。

| 表/数据 | 关键字段或映射 | 删除与兼容约束 |
| --- | --- | --- |
| `schema_migrations` | 版本号、迁移标识、完成时间 | 每个 schema 迁移和版本记录同一事务提交；未知更高版本只读报错，不降级写入 |
| `preferences` | appearance、language | 校验枚举；从缺省值初始化时与旧版本一致 |
| `projects` | id、name、path、description | 唯一化使用现有规范化路径规则；移除项目不删除源文件或会话 |
| `chats` | id、title、updatedAt、projectId、projectPath | 保留目录快照和已移除项目引用；历史缺少 `projectPath` 不能凭空推断 |
| `skills` | id、name、description、filePath、enabled | 保存引用，不复制或删除技能源文件 |
| `mcp_servers` | id、name、type、command/args 或 URL、enabled | 保留各类型配置；不引入明文秘密；校验名称归一化冲突 |
| `schedules` | 原 Schedule 全字段，包括 prompt、cron、timezone、projectId、skillId、nextAt、gatewayUrl、modelId、enabled | 保留计划模板和已记录的目标模型；不迁移成云端计划 |
| `schedule_runs` | 原 ScheduleRun 全字段，包括 scheduleId、时间、状态、chatId、detail | 删除计划不能自动清除历史或停止运行；可保留指向已删除计划/项目/技能的历史 ID |

所有 ID、状态枚举、可空字段和时间毫秒值保留原义；迁移时缺少非必需字段使用明确兼容默认值。旧会话原先保留了指向已删除项目的引用，因此不使用会级联删除历史的外键；必要时对引用做业务层校验。运行记录当前最多 1000 条，迁移应保留源文件中实际全部记录，不额外裁剪。

对已有源格式外的字段：保留不可变原始备份，并在预检时记录字段名/结构版本差异；不得默默丢弃无法识别的记录。遇到类型损坏、重复 ID、路径冲突或新格式无法无损表达时停止迁移并给出诊断，不自动丢弃、修正或重新分配 ID。诊断不包含提示词、凭据或文件原文。

### E10 访问层实现与边界

`apps/desktop/electron/metadata-store.ts` 提供项目、偏好、对话、技能、MCP、计划及运行记录的独立访问方法。打开已有数据库先进行只读 schema 预检，拒绝未知版本或不完整结构；启用 WAL 前通过 E09 SQLite 版本门禁。建表与 schema 版本记录在同一事务中提交。

项目重绑、删除会在事务中保留旧对话目录；计划的条件推进和运行记录插入在同一事务提交，冲突或插入失败回滚。计划记录读取按插入顺序倒序；E11 从现有最新在前的 JSON 导入时必须保持相同展示顺序。表不对历史引用设置级联删除。完整字段合法性和无损预检由 E11 负责，E10 不能代替迁移、备份或数据修复。

验证：`pnpm test:metadata` 和 `pnpm test:packaged-metadata` 均使用临时库，覆盖 schema 初始化及拒绝、读写和重开、重绑回滚、历史保留、条件触发及插入失败回滚；打包测试使用应用内的原生 SQLite。现有应用启动路径仍不调用该访问层，不会自动创建或迁移用户数据库。

## 4. 旧 JSON 到 SQLite 的一次性迁移

以 **旧 JSON 不修改、临时库构建、校验后原子切换、单一权威源** 为原则。下面是实现契约，不是当前已实现行为。

1. 获得单实例锁并暂停调度及写入。检查 `userData` 是否有旧配置、目标数据库、迁移临时文件或未完成标记；仅在不存在任何已有数据及迁移痕迹时认定为全新安装。源缺失但存在会话文件、残留临时文件或损坏痕迹时进入恢复流程，不创建空状态。
2. 先对 `settings.json` 做只读解析和结构预检，再建立受限权限的不可变原始备份和摘要；读取/复制完成后比对字节及摘要。若旧 JSON 不存在但已有其他数据，停止并提示；无效 JSON、权限不足或磁盘空间不足均保留原文件并停止。
3. 在同一文件系统的临时位置创建全新临时库，使用支持安全提升的 `better-sqlite3` 版本；建立 schema、导入并在同一事务中写入迁移元数据和源摘要。不得直接对现有目标库导入，也不得重新生成现有 ID。
4. 对照源数据校验每一类记录数量、ID 集合及所有映射字段、缺省字段、目录快照、定时状态和引用；对合法的失效引用保留并标注，不把不可访问目录或缺失 JSONL 当作可删记录。验证 SQLite `integrity_check`，同时记录缺失或不可读的会话文件供 UI 提示，不更改 JSONL。
5. 关闭临时库，按实际 SQLite journal 模式正确完成一致性处理；保证临时库和目标在同一文件系统，用不覆盖已有目标的方式发布。发布前后必要的文件与目录同步由实现和平台测试确认，不将单次 rename 宣称为跨文件事务或断电绝对安全。
6. 下次启动若目标存在，先验证 schema/完整性及迁移元数据后再作为唯一权威源；旧 JSON 保留为只读备份，不再写回。迁移中断时依据目标库、迁移元数据和源备份判断重试/恢复；目标存在但无有效完成证明时禁止覆盖它或自动导入第二次。
7. 仅在数据库成功打开并完成恢复后恢复调度；原本 `running` 的任务标记为中断/失败并可见，过期计划按现有规则记录错过、不自动补跑，不因迁移自动重放外部副作用。

旧版客户端仍会读写 `settings.json`，不能让新版数据库和旧版 JSON 同时成为权威源。迁移后不支持直接降级为旧版继续写：需先停止所有实例，经显式导出/兼容转换或恢复预迁移备份，并告知恢复备份会丢失备份之后的新数据。此降级机制在 E12/E13 完成前不得宣传可用。

## 5. 备份、损坏检测与恢复

- **备份范围**：迁移前保存原始 `settings.json`；后续 SQLite 采用 SQLite 在线备份 API 生成一致快照，单独保留 schema 版本与校验结果。运行中的 WAL 数据库不能只复制 `.db` 当作完整备份；安全一致的在线备份方式见 [SQLite Online Backup API](https://www.sqlite.org/backup.html)。备份过程须防止并发写入导致的跨文件误配。
- **Pi 会话和网关**：SQLite 快照不包含 Pi JSONL 或 `gateway.json`。项目文件不属于应用备份。需要跨文件一致的导出/完整恢复时先停止相应会话及调度，在静止状态下分别备份并生成清单；跨文件不具备原子提交，清单标注各自时间和不一致风险。`safeStorage` 密文可能依赖原设备/系统账户，不能保证跨设备解密；凭据不可用时提示重新输入，不能要求输出明文。
- **保留策略**：迁移前备份与其校验清单至少保留至迁移和安装升级验收完成；自动清理、容量上限及保留数量作为 E12 的可配置实现与测试项，禁止无提示删除唯一可用备份。备份包含任务内容、项目路径及可能的加密密钥，目录/文件仅对当前用户可读，诊断导出默认不包含备份正文。当前原型以排他创建保证应用不会覆盖备份，并非操作系统级不可变文件。
- **检测**：打开失败、schema 版本不支持、`integrity_check` 失败、源文件无效、磁盘已满或权限不足均显示明确的错误类别；禁止把错误视为首次安装、覆盖原库或新建空库继续运行。不能把所有 I/O 错误都判作数据库损坏。
- **恢复**：默认停止写入和定时执行，保留原库、关联 WAL/SHM 与原始文件；先提供导出诊断及查看可用备份的入口。由用户选择备份，在临时位置验证，再创建待恢复状态；恢复前先保留现有状态，在停写并关闭连接后替换，重开并验证。恢复后展示备份时间及可能丢失的较新变更；失败保留原状态和备份，不能自动删库或启动空库。
- **会话异常**：索引存在但 JSONL 缺失/损坏时保留索引并提示，允许用户导出诊断；游离 JSONL 单独列为待恢复，不根据文件名或 UI 文本擅自重建 Pi 历史。会话恢复方案和工具结果一致性需遵守已安装 Pi SDK 的 SessionManager 行为。

## 6. 验收与实施拆分

E07 完成决策与设计；E09 和 E10 已完成独立实现与本机/打包验证，E11、E12 部分实现，E13、E14 尚未实现，逐项按计划更新：

1. **E09 原生依赖和单实例（已完成）**：`better-sqlite3` 13.0.3 / SQLite 3.53.4，运行时 WAL 版本门禁，ARM64 开发/打包临时库验证，以及单实例锁测试；macOS 13 实机仍属 E05。
2. **E10 schema 与访问层（已完成）**：版本迁移、查询接口、事务及无级联历史保留；同一计划到期状态与运行记录在一个事务内原子更新。应用接入另属 E11。
3. **E11 旧数据迁移（部分实现）**：隔离迁移原型已覆盖预检、备份、临时库、字段对照及模拟中断重试；启动接入、新安装、缺失会话诊断及异常验收待完成。
4. **E12 备份与恢复（部分实现）**：隔离在线快照、清单校验、恢复候选及保留建议已实现；应用接入、实际恢复、容量策略和真实故障验收待完成。
5. **E13 集成和升级验收**：项目/历史/计划/技能/MCP 全链路、迁移前后对照、进程崩溃、重复启动、安装升级和回滚限制；验证 Pi JSONL、`gateway.json`、项目文件及技能源内容不变。
6. **E14 计划任务一致性**：模拟同时触发、进程终止、错过和跨重启状态；保证状态和记录原子更新，外部副作用不宣称恰好一次。

后续若将 SQLite 接入应用，应先完成与切换相关的迁移、数据保留及验证；当前不得将 SQLite 描述为已交付存储。macOS 13 实机验收见精简计划。

## E12 原型边界（2026-11-04）

`metadata-backup.ts` 使用已安装 better-sqlite3 的在线备份 API，在私有目录创建仅包含 SQLite 元数据的快照；清单记录 SHA-256、长度、schema 版本及校验状态。清单只在快照校验完成后写入；未完成及不可用备份不会被自动删除。恢复准备仅创建并复核独立候选，不替换现有数据库。保留算法只给出候选，不执行删除。

这些 API 尚未连接应用启动、调度、设置或恢复界面。它们不备份 Pi JSONL、`gateway.json` 或项目文件，不能提供跨文件一致恢复；清单摘要用于检测意外损坏，不构成防篡改签名。没有经过真实断电、磁盘满、权限异常和进程强退验收。
